DocIntel MVP Build Plan
========================

Goal
----
Build an AI research assistant that lets a user upload PDF documents, ask
questions about them, receive an answer grounded in the documents, and see the
source document and page numbers used for the answer. Groq provides the chat
model through its API, while ChromaDB handles local vector storage and local
embeddings.

MVP scope
---------
Included:
- PDF upload
- Text extraction with PyMuPDF
- Text chunking
- Local embeddings using ChromaDB's default embedding function
- Local ChromaDB vector storage
- Similarity search
- Answer generation with a Groq API chat model
- Source citations containing filename and page number
- FastAPI backend
- Streamlit frontend
- Basic tests and documentation

Not included yet:
- PostgreSQL or pgvector
- Redis or background workers
- Authentication and multiple users
- AWS, Azure, Kubernetes, or CI/CD
- MCP
- Complex agents and tool calling
- Hybrid search or reranking
- Web search
- DOCX, CSV, or other file types
- Production monitoring

Phase 0: Confirm the setup
--------------------------------
1. Confirm Python and Git are installed.
2. Create and activate the virtual environment:
   python3 -m venv .venv
   source .venv/bin/activate
3. Install dependencies:
   python -m pip install -r requirements.txt
4. Create a Groq account and obtain an API key.
5. Add the key to a local `.env` file:
   GROQ_API_KEY=your_key_here
6. Choose a currently available Groq chat model and add it to `.env`:
   GROQ_MODEL=your_model_name
7. Test the Groq API before writing application code.
8. Confirm that ChromaDB can initialize its default local embedding model.

Phase 1: Create the project structure
-------------------------------------
Create:
- app/main.py              FastAPI application and API routes
- app/config.py            Environment variables and application settings
- app/pdf_loader.py        PDF text extraction with page metadata
- app/embeddings.py        ChromaDB embedding configuration
- app/rag.py               Chunking, indexing, retrieval, and answer generation
- frontend/streamlit_app.py Streamlit user interface
- data/documents/          Uploaded PDF files
- chroma_db/               Local ChromaDB persistence directory
- tests/                   Automated tests
- .env.example             Example configuration
- .gitignore               Ignore secrets, virtual environment, data, and database
- README.md                Setup, usage, architecture, and limitations

Phase 2: Implement PDF ingestion
--------------------------------
1. Accept a PDF file from the API.
2. Save it under data/documents/.
3. Open the PDF with PyMuPDF.
4. Extract text page by page.
5. Preserve metadata for every page:
   - source filename
   - page number
6. Reject unsupported files and empty PDFs with clear errors.
7. Add a test using a small sample PDF.

Phase 3: Implement chunking
---------------------------
1. Split extracted page text into manageable chunks.
2. Start with a recursive character text splitter.
3. Use a chunk size around 800 to 1,000 characters.
4. Use an overlap around 100 to 150 characters.
5. Preserve the source and page metadata on every chunk.
6. Test that chunks are created and retain correct page metadata.

Phase 4: Implement embeddings and ChromaDB
------------------------------------------
1. Configure ChromaDB's default embedding function for local embeddings.
2. Create a persistent local ChromaDB collection.
3. Generate an embedding for each chunk.
4. Store each chunk, its embedding, and its metadata.
5. Use stable document IDs so re-uploading a file does not create unwanted
   duplicates.
6. Add a way to clear or rebuild the collection during development.
7. Test that an indexed document can be retrieved for a relevant query.

Phase 5: Implement retrieval
-----------------------------
1. Convert the user question into an embedding.
2. Search ChromaDB for the top-k relevant chunks.
3. Start with k=4 or k=5.
4. Return the chunk text and metadata.
5. Remove duplicate source/page citations.
6. Handle the case where no useful context is found.
7. Test retrieval with questions whose answers are known to be in the sample PDF.

Phase 6: Implement grounded answer generation
----------------------------------------------
1. Configure a Groq chat model using `GROQ_API_KEY` and `GROQ_MODEL`.
2. Build a prompt containing:
   - the retrieved context
   - the user question
   - grounding instructions
3. Instruct the model to answer only from the supplied context.
4. Instruct it to say that the answer is not available in the documents when
   the context does not contain the answer.
5. Generate the final answer.
6. Return the answer together with the retrieved source metadata.
7. Keep citations generated by the application rather than trusting the model
   to invent page numbers.
8. Test both a question with an answer and a question outside the document.

Phase 7: Build the FastAPI backend
----------------------------------
Implement these initial endpoints:

POST /documents/upload
- Accept one PDF.
- Extract, chunk, embed, and store it.
- Return filename, page count, and chunk count.

POST /query
- Accept a question.
- Retrieve relevant chunks.
- Generate a grounded answer.
- Return answer and citations.

GET /health
- Return a simple healthy response.

1. Add Pydantic request and response models.
2. Add clear HTTP errors.
3. Keep the core RAG logic separate from route functions.
4. Test endpoints with FastAPI TestClient.

Phase 8: Build the Streamlit frontend
--------------------------------------
Purpose
-------
Create a simple user interface that communicates with the FastAPI backend.
Streamlit should handle presentation and user interaction only. PDF extraction,
chunking, embeddings, ChromaDB, retrieval, and Groq generation must remain in
the backend.

Frontend file
-------------
Implement the interface in:

frontend/streamlit_app.py

Frontend responsibilities
--------------------------
- Collect a PDF from the user.
- Send the PDF to the upload endpoint.
- Collect a question from the user.
- Send the question to the query endpoint.
- Display the answer and source citations.
- Display loading, success, and error states.

Backend URL configuration
-------------------------
1. Choose a default backend URL:
   http://127.0.0.1:8000
2. Allow the URL to be configured through an environment variable such as:
   API_URL=http://127.0.0.1:8000
3. Load the environment variable from `.env`.
4. Keep the backend URL in one variable instead of repeating it throughout the
   frontend.

Page layout
-----------
Organize the page into these areas:

1. Page title and short description.
2. Backend connection section.
3. Document upload section.
4. Indexing result section.
5. Question section.
6. Answer section.
7. Sources section.

Step 1: Add page configuration
------------------------------
1. Set the page title.
2. Set a suitable layout.
3. Add the application title.
4. Add a short description explaining that answers come from uploaded PDFs.

Step 2: Add backend health checking
-----------------------------------
1. Add a button for checking the backend.
2. Send a GET request to `/health`.
3. Set a reasonable request timeout.
4. Show a success message when the response status is successful.
5. Show an error message when the backend is unavailable.
6. Catch connection and timeout errors so the UI does not crash.

Step 3: Add PDF upload controls
-------------------------------
1. Add a file uploader that accepts PDF files only.
2. Add a process or upload button.
3. Do not send a request when no file has been selected.
4. Show a warning when the user presses the button without a file.
5. Read the selected file as bytes.
6. Send it as multipart form data to:
   POST /documents/upload
7. Set a longer timeout because embedding a document can take time.

Step 4: Handle the upload response
----------------------------------
The backend should return information similar to:

{
    "source": "paper.pdf",
    "pages": 10,
    "chunks": 42
}

1. Check whether the response was successful.
2. Display the uploaded filename.
3. Display the number of extracted pages.
4. Display the number of created chunks.
5. Tell the user that the document is ready for questions.
6. Display backend error details when indexing fails.
7. Store the latest indexing result in Streamlit session state if it should
   remain visible after a page rerun.

Step 5: Add question controls
-----------------------------
1. Add a text input or text area for the question.
2. Add an ask button.
3. Add a control for the number of retrieved chunks.
4. Use a default value such as 4.
5. Do not send an empty question.
6. Show a warning when the ask button is pressed without a question.

Step 6: Send the question to the backend
----------------------------------------
1. Build a JSON request:

{
    "question": "What is machine learning?",
    "number_of_results": 4
}

2. Send the request to:
   POST /query
3. Set a timeout long enough for retrieval and Groq generation.
4. Show a loading indicator while waiting.
5. Catch connection, timeout, and HTTP errors.

Step 7: Display the answer
--------------------------
The backend response should contain:

{
    "answer": "Generated answer...",
    "sources": []
}

1. Check that the response is successful.
2. Display the answer in a clearly labeled section.
3. Handle a missing or empty answer gracefully.
4. Do not generate or edit the answer in the frontend.
5. Keep the answer returned by the backend unchanged.

Step 8: Display citations
-------------------------
1. Read the `sources` list from the response.
2. Display each source with a number.
3. Show the filename and page number.
4. Use this format:
   [1] paper.pdf - Page 4
5. Display a message when no citations are returned.
6. Do not ask the LLM to create citations in the frontend. Citations must come
   from the metadata returned by the backend.

Step 9: Add user-facing error states
------------------------------------
Handle these cases clearly:

- FastAPI is not running.
- The selected file is not a PDF.
- The uploaded PDF is empty or has no extractable text.
- PDF indexing fails.
- The question is empty.
- The query request times out.
- The Groq API returns an error through the backend.
- The backend returns no sources.

Every error should explain what failed without displaying API keys or other
secrets.

Step 10: Use Streamlit session state
------------------------------------
Use session state only for small UI values, such as:

- Backend URL
- Latest indexing result
- Latest answer
- Latest source list

Do not store the full PDF, embeddings, or ChromaDB data in Streamlit session
state. Those belong in the backend and local storage.

Step 11: Run the frontend
-------------------------
1. Activate the virtual environment.
2. Start FastAPI in the first terminal:
   uvicorn app.main:app --reload
3. Start Streamlit in the second terminal:
   streamlit run frontend/streamlit_app.py
4. Open the URL printed by Streamlit, usually:
   http://localhost:8501

Step 12: Test the frontend manually
-----------------------------------
1. Open the Streamlit page.
2. Check the backend health status.
3. Upload one valid technical PDF.
4. Confirm the indexing result is displayed.
5. Ask a question whose answer is clearly present.
6. Confirm the answer appears.
7. Confirm filename and page citations appear.
8. Ask a question not covered by the PDF.
9. Confirm the system reports that the answer was not found.
10. Try submitting an empty question.
11. Try starting Streamlit while FastAPI is stopped.
12. Try uploading an invalid file.
13. Upload a second PDF and confirm it can also be indexed.

Frontend completion condition
-----------------------------
The frontend phase is complete when a user can:

1. Open the Streamlit interface.
2. Check the backend connection.
3. Upload a PDF.
4. Wait for indexing to finish.
5. Ask a question.
6. See a grounded answer.
7. See the source filename and page number.
8. Understand errors without reading the terminal.

Phase 9: Complete MVP testing
-----------------------------
1. Confirm the Groq API is available.
2. Start the FastAPI server.
3. Start Streamlit.
4. Upload a real technical PDF.
5. Ask a question with an obvious answer in the PDF.
6. Confirm the answer is based on the document.
7. Confirm page citations are displayed.
8. Ask a question not covered by the PDF.
9. Confirm the system says it does not know instead of guessing.
10. Test a multi-page PDF.
11. Test an invalid file and an empty PDF.
12. Test restarting the application and reusing the local ChromaDB data.

Phase 10: Documentation and MVP completion
-------------------------------------------
1. Write the exact setup commands in README.md.
2. Document the Groq API key and selected model configuration.
3. Add the application architecture diagram.
4. Explain the RAG pipeline in plain language.
5. Document the API endpoints.
6. Document known limitations.
7. Add screenshots or a short demo video later.
8. Add a final MVP checklist.

MVP completion checklist

- [ ] Requirements install successfully

- [ ] ChromaDB local embedding function initializes
- [ ] PDF upload works
- [ ] Text extraction preserves pages
- [ ] Chunking works
- [ ] ChromaDB persists vectors locally

Recommended implementation order
--------------------------------
Build and test one vertical slice at a time:

1. PDF file -> extracted page text
2. Extracted text -> chunks with metadata
3. Chunks -> ChromaDB embeddings
4. Question -> retrieved chunks
5. Retrieved chunks -> grounded answer
6. RAG pipeline -> FastAPI endpoint
7. FastAPI endpoint -> Streamlit UI
8. Full workflow -> tests and README
